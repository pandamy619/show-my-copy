# Security policy

## Reporting a vulnerability

Please report vulnerabilities privately through GitHub: **Security → Report a vulnerability** in this repository. Do not open a public issue, and do not include real clipboard contents or passwords in the report.

## Supported versions

There are no releases yet. Security fixes go to the `main` branch; once releases exist, only the latest one will get them.

## Security model

### Today (0.1.0)

- **No network.** The app itself makes no connections: it is sandboxed without network entitlements, so macOS blocks any connection it tries to make. This covers the app's own process only. Work macOS does for it in system processes, such as QuickLook drawing file thumbnails, runs outside the app's sandbox (see below). CI builds the Release configuration with ad-hoc signing and checks its signed entitlements (`make security`).
- **Stored on this Mac only.** The history is saved in the app's sandbox container (`~/Library/Containers/…/Data/Library/Application Support/ShowMyCopy/History/History.store`, a SwiftData/SQLite store) so it survives quitting the app. It is never synced (no CloudKit) or sent anywhere, and the folder is excluded from Time Machine and other backups. Clear History in Settings deletes it from disk as well, together with a damaged copy (see below) and, when the history could not be opened at this launch, the store that could not be opened. When it keeps pinned entries (the default while there are any), it deletes the other entries, saved passwords waiting for the key and a damaged copy, and leaves the pinned entries and what may hold pinned entries this launch did not load: records it did not load and a store that could not be opened; removed and expired entries are deleted from disk right away, or with the next change when writing failed. The first launch of this build deletes, without reading it, the history that development builds saved in an earlier format directly in `Application Support/ShowMyCopy` (database, side files, damaged copy and `Blobs/`).
- **History is kept for a limited time (data minimisation).** By default an entry is removed 8 hours after it was last copied; copying the same content again starts its time over. Settings → History → Remove items after offers 1 hour, 8 hours, 24 hours, 7 days, 30 days or Off; with Off, entries stay until the entry limit, the size limit or Clear History removes them. While the app runs it checks on every look at the clipboard (twice a second, less often while macOS lets the app nap), and again as soon as the Mac or its displays wake or the screen is unlocked (also when the screen is still locked after the Mac wakes) and at launch, so entries that expired while the Mac slept or the app was not running are removed before the history can be shown. Removing an entry deletes its database record and its image and thumbnail files (but see "Deleted entries may stay on the disk" below). Saved passwords keep their own, shorter expiry; whichever comes first removes them. Pinned entries are kept regardless of age (see below). A damaged copy of the history is out of reach of this limit (see below).
- **Images are files in the same folder.** A copied image is saved unchanged, with a PNG thumbnail of at most 256 pixels, as separate files in `Application Support/ShowMyCopy/History/Blobs/` in the container, also excluded from backups; the database holds only their IDs, size and type. They are not encrypted (FileVault protects them at rest). A copied image is listed at once and saved in the background a moment later; until then its bytes are only in the app's memory and its entry is not written to the database, and quitting waits up to 2 seconds for it. Removing an entry, the history limits and Clear History delete its files; files no entry uses any more (for example after a crash) are deleted at the next launch, but not while a damaged copy of the history is kept or the history could not be read, since those may still use them. Files that an image or thumbnail being saved is about to use are left alone by all of these until it is done; if its entry is gone by then, they are deleted. Images are read with ImageIO, in the app's process, only to measure them, draw the thumbnail and show it. ImageIO picks the format from the bytes, not from the type an app copied them as, so before ImageIO decodes anything the app checks the first bytes: only PNG, JPEG, HEIC, TIFF, GIF, WebP and BMP data are decoded, copied data must be the format it was copied as, and ImageIO must read it as that same format (a RAW photo, which starts like a TIFF, is rejected). Anything else is not recorded. The width and height in the image's header are checked before any pixel is decoded: an image of more than 120 megapixels is recorded without a thumbnail and its preview shows a placeholder, so a small file that declares a huge image (a decompression bomb) is never decoded. The full image is read only when you open its preview in the history window, decoded at most 2048 pixels on its longer side, and dropped when the preview closes. The preview of styled text reads the copied data as RTF only (never as HTML) and drops attachments and links, so it cannot load anything or open a link.
- **Files are references only.** For copied files the history keeps the path, the name and, when the sandbox allows reading it, the size: never the contents and no access rights (no security-scoped bookmarks). The size is read just after the copy, in the background, within 1 second for the whole copy. The app never looks up a copied path on a network volume or under an automounted folder (`/net`, `/Network`, autofs maps), since looking a path up there can make macOS contact a server: such files show no size, no thumbnail and no "may be unavailable" mark, and their icon comes from the file name's extension. Files on other disks and in iCloud or other cloud folders are looked at only in the background, within time limits. Where a path is is decided from the path and the list of mounted volumes, without following symbolic links; a link on this Mac that leads to a network location is followed by the background checks. The app cannot follow a moved file, and in the sandbox it often cannot tell a deleted file from one it is not allowed to look at, so it can only say a file *may* be unavailable. Paths and file names are stored in plain text in the database. The history window shows where a file is from the saved path alone, as text, without looking the path up; to shorten the home folder to `~` it asks the user database for the user's home folder once (`getpwuid_r`), since in the sandbox `NSHomeDirectory()` is the app's container. A folder the user selects there and copies with ⌘C is put on the clipboard by the app itself, as plain text with the `org.nspasteboard.source` marker and the app's own `com.pandamy619.ShowMyCopy.unrecorded` marker (an empty string), and is not recorded, also when the app finds it at the next launch or after a pause: it is skipped by the second marker alone, before its text is read. Other apps write `org.nspasteboard.source` too, so that marker is not used to skip anything; its menu offers Copy only (no Look Up, Services or Share), and the text is offered to no service. The address of the source code in Settings → About is copied the same way.
- **Copied photos and videos are read once for a thumbnail.** When the first files of a copy (up to 4) are images or movies, the app reads each of them once, right when it is copied, to make a PNG thumbnail of at most 256 pixels with QuickLook (`QLThumbnailGenerator`, which draws a frame of a video). The sandbox allows this only because reading the file URLs from the pasteboard gives the app access to those files until it quits; it needs no file entitlement for this (its one file entitlement, below, is for Choose an App… only). Only the thumbnail is kept, in the `Blobs` folder next to image thumbnails, not encrypted, and deleted with its entry; nothing else of the file is copied or kept. QuickLook reads the file and draws the thumbnail in system processes (or in a Quick Look extension another app installed), outside the app's sandbox and with their own rights, which can include the network; the app does not control what they do. So the app limits what it asks for:
  - It does not ask QuickLook for files that are not local: it skips URLs that are not file URLs, files on network volumes, and iCloud or other cloud files whose data is not on this Mac (not downloaded, or "dataless" placeholders).
  - It asks only about PNG, JPEG, HEIC, TIFF, GIF, WebP and BMP images and QuickTime (.mov), MPEG-4 (.mp4) and .m4v movies, matched by their exact type. SVG, PDF, RAW photos, QuickTime links, playlists and every other format, including any that only another app's Quick Look extension draws, keep their icons.
  - It reads the header of an image file first, in its own process: the file must start like the format its type names, ImageIO must read it as that format, and it must be at most 120 megapixels. Of a movie it reads only the headers of the boxes the file is made of: a reference movie, or one without media data of its own, keeps its icon. A crafted movie could still point one of its tracks at media elsewhere next to media of its own; whether the system's movie thumbnailer follows that is up to macOS. Files that cannot be read, or take longer than 1.5 seconds (2 seconds for the whole copy), keep their icons. A thumbnail shows what the photo or video looked like when it was copied, even after the file is changed or deleted.
- **Passwords are not kept by default.** Items marked as concealed (see [nspasteboard.org](http://nspasteboard.org)) or with the older markers some password managers use, and anything copied while a known password manager is the frontmost app (1Password, Bitwarden, Passwords, Keychain Access, KeePassXC, Strongbox, LastPass, Proton Pass, Enpass, Keeper), are not recorded, and their text is not read. Items marked as transient or auto-generated are never stored.
- **Excluded apps.** In Settings → Excluded apps you pick apps whose copies are never recorded. On every clipboard change the app first asks macOS which app is in front (`NSWorkspace.frontmostApplication`) and compares its bundle identifier, without regard to letter case, with the list. For an excluded app it reads nothing from the clipboard, not its types, its text or its data: it records nothing, does not take the change for an emptied clipboard (so nothing is removed or hidden), and the entry copied before is no longer marked as the one on the clipboard. This check comes before the password manager check, so an excluded password manager is not read even with Save passwords on. The list keeps only each app's bundle identifier and name, in the app's UserDefaults (it is a setting, not clipboard data); no path, bookmark or file access is kept, so it applies to the app wherever it is installed. Apps are added from the apps open now with a Dock icon (`NSWorkspace.runningApplications`), or with Choose an App…, an open panel (below). Settings show each app's icon as the workspace draws it from the installed app, only when the app is on the startup disk; otherwise a generic icon.
- **Deleting one entry.** Deleting an entry in the history window (⌘⌫) deletes its database record at once, in one transaction. Its files (an image and its thumbnail, thumbnails of copied photos and videos) are kept until the window closes or another entry is deleted, so ⌘Z can bring the entry back; Clear History, the history limits and the sweep at launch leave them alone meanwhile. If the app quits first, they are deleted at the next launch like any file no entry uses. When the deleted entry is the one on the clipboard, the clipboard is emptied only if its change count is still the one at which the app recorded that entry, so nothing was copied since: a newer copy, a password the app did not record, or anything the app has not read yet is never emptied. macOS has no way to empty the clipboard only if it still holds a given item, so the check and the clear run back to back on the main thread; another app writing in that instant could still be emptied. Undo does not put the entry back on the clipboard.
- **Pinned entries are kept until you remove them.** Pinning an entry (⌘P in the history window) is a choice to keep it: the age, entry and size limits never remove it, and a clipboard emptied soon after it was copied is never taken for a password manager clearing a password. So a pinned entry stays in the history, and on disk, for as long as it is pinned, also past the age limit you chose. It is saved like any other entry, in the same record: the pin and the time it was pinned are fields that record already had, so pins need no new saved format. It is deleted with ⌘⌫, by Clear History with "Also remove pinned entries" checked, or by the limits after you unpin it (unpinning puts it at the top of the history, so its time starts over then). Passwords cannot be pinned: they keep their own expiry, and an entry that turns out to be a password is unpinned when it is hidden. At most 50 entries are pinned (`RetentionPolicy.maximumPinned`). Pinning one more, or ⌘Z bringing back a deleted pinned entry while 50 are pinned, unpins the oldest pinned entry in the same transaction; it goes to the top of the history dated now, as when you unpin it, so the limits count it again from then. A history saved with more than 50 pinned (by an earlier build) keeps the newest 50 pinned at launch and unpins the others in the launch's one transaction. The cap bounds what pinning keeps outside the limits, not how much: pinned entries do not count toward the size limit, so 50 pinned images of up to 20 MB each, with their thumbnails, can keep about 1 GB on disk beyond it. Settings → Storage counts them in the history size.
- **Cleared passwords leave the history.** Password managers empty the clipboard a while after copying a password. When the clipboard is emptied within 3 minutes of copying text that is still on it, and it is still empty half a second later, that entry is removed, or hidden with an expiry if you save passwords. Images and files are never taken for passwords this way, and an app that empties the clipboard just before writing to it does not remove anything. While the Mac sleeps or the screen is locked the app does not look at the clipboard, so a clipboard emptied meanwhile is noticed right after waking or unlocking. When it was emptied is not known then, so it counts when the Mac went to sleep or was locked within 3 minutes of the copy and emptying the clipboard was the only change to it since; the hidden entry's expiry counts from when the Mac went to sleep or was locked. A clipboard emptied while an excluded app is in front is not looked at, so it removes nothing.
- **Saving passwords is opt-in.** With Settings → Passwords → Save passwords on, passwords are kept masked in the history (the mask does not show their length), revealed one row at a time with the eye button and hidden again when the window closes, left out of text search, never read out by VoiceOver, and removed after 1 minute, 10 minutes (default) or 1 hour. While the Mac sleeps or the screen stays locked, a password whose time is up is removed as soon as the Mac or its displays wake or the screen is unlocked. Turning the setting off removes them at once. A password copied back from the history is marked as concealed and kept off Universal Clipboard, so other clipboard managers and your other devices do not get it. Settings → Storage shows the passwords' total size rounded up to whole kilobytes, and adds that rounded size to the history size and to what Clear History or a lower limit frees, so none of them tells a password's length.
- **Passwords leave the clipboard with the history.** When a saved password expires, or is removed because Save passwords is turned off, and the clipboard still holds it, the clipboard is emptied too. That includes a password you copied back from the history. As when deleting an entry, the clipboard is emptied only while its change count is still the one at which the app recorded the password or put it there, so nothing was copied since: anything else, including a password the app did not save, is never emptied, and the app does not take the emptied clipboard for a copy or for a password manager clearing a password. macOS cannot empty the clipboard only if it still holds a given item, so the check and the clear run back to back on the main thread; another app writing in that instant could still be emptied. Entries removed for their age are left on the clipboard.
- **Saved passwords are encrypted on disk.** With Save passwords on, each password is encrypted with AES-256-GCM before it is written, padded so its size does not tell the password's length. No hash or preview of a password is stored: a plain hash of a short password could be checked against a list of common passwords. The key is created on this Mac, kept in your Keychain and never synced to iCloud. The app asks the Keychain for it only when a password is saved or a saved password is loaded, so with Save passwords off it never touches the Keychain, and it asks in the background, so a Keychain prompt never holds up the app; until the key is read, saved passwords wait on disk, still encrypted, and new ones are kept in memory. Saved passwords that have expired, and all saved passwords once Save passwords is off, are deleted at launch without asking for the key. Turning Save passwords off also deletes a damaged copy of the history at once, since it may hold encrypted passwords. If the key cannot be read, because you deny Show My Copy access to it or the Mac is locked, new passwords are kept in memory only until you quit and Settings → Storage says so. Passwords saved before stay on disk unopened: they still expire on time and are deleted when you turn Save passwords off or clear the history, and the app tries the key again when you unlock the Mac (after a denial, at the next launch). Only passwords that a key the app did read cannot decrypt, because the key was replaced, are deleted. Everything else is still saved.
- **Passwords are only kept as text.** A secret (marked, or copied from a password manager) is read as plain text only, so a password is never stored as styled text, an image file or a file reference; an image or files marked as concealed are not recorded at all.
- **One file entitlement: reading the app you choose.** Besides the sandbox, the app has one entitlement, `com.apple.security.files.user-selected.read-only`, and uses it only for Settings → Excluded apps → Choose an App…. It lets the app read, never write, what you pick in an open panel. macOS draws the panel outside the app (the sandbox's Powerbox), so the app learns nothing about your disk while you browse; the app sets it to offer only apps (`allowedContentTypes = [.application]`), one at a time, no other folders, starting in /Applications. When you pick an app, macOS lets the app read that app bundle until the app quits or gives the access back. The app reads the bundle's `Contents/Info.plist` once, in the background and at most 512 KB of it, for two values, the bundle identifier and the name, and then gives the access back (`stopAccessingSecurityScopedResource`); whatever happens, the access ends when the app quits. It keeps no path, URL or security-scoped bookmark, so nothing gives the access back at a later launch; only the bundle identifier and the name go into the list, as for an open app. An app without a bundle identifier and Show My Copy itself are not added, and Settings say why. The entitlement is in `Config/ShowMyCopy.entitlements`, and the app target's `ENABLE_USER_SELECTED_FILES = readonly` says the same so that Xcode shows what the app is signed with. `make lint` and `make security` check that the two agree, and reject the entitlement or the setting in any other target or entitlements file, in the Control Center extension and in anything the app embeds, and reject read-write access everywhere.
- **Control Center extension.** On macOS 26 and later the app embeds a small WidgetKit extension for the Control Center button. It is sandboxed with no other entitlement (not even the app's user-selected read-only files) and no network access, like the app, signed with the hardened runtime, and `make security` checks it the same way. It reads no history and no clipboard: it shows a fixed label and icon, and the system runs the button's action in the app's process, which opens the history window. The app and the extension share no data (no App Group).
- **Minimal permissions.** The app asks for no permission unless you turn on pasting into the active app (below), and never for Input Monitoring.
- **Pasting into the active app is opt-in.** With Settings → General → Paste after choosing an entry on (off by default), choosing an entry with Enter copies it, closes the history window and sends ⌘V to the app that was in front (⌥Enter or ⌥-click only copies; with the setting off it is the other way round). Sending ⌘V needs macOS's permission to post events, which System Settings list under Privacy & Security → Accessibility. The app asks for it with `CGRequestPostEventAccess` only when you turn the setting on (macOS shows its own alert while it still asks), and checks it with `CGPreflightPostEventAccess`, which shows nothing, when Settings open or come to the front and before every paste; it does not use `AXIsProcessTrusted`. In general this permission lets an app post any keyboard or mouse event to the app in front. Show My Copy uses it for one thing: after you choose an entry, it waits until the window server no longer shows the history window (at most 0.25 seconds) and then 0.15 seconds more, so the app in front can make its window key and focus its field again, and posts one ⌘V: ⌘ down, V down and up, ⌘ up, to the login session (`kCGSessionEventTap`), with only ⌘ set. It posts only while the clipboard still holds what the app just put there (its change count is unchanged), the same app as when you chose is still in front and the history window is not on screen (it does not paste when the window stayed or you opened it again); it never posts to itself, for example with Settings in front. All four events are made before the first is posted, so ⌘ is never left down. It does not use the rest of the Accessibility API (it never reads other apps' windows or text), and it never reads keyboard input: no event tap, no event monitor, no Input Monitoring. The key is found from your keyboard layout, read with Text Input Sources, which tells only what each key types. Passwords are pasted the same way: they stay marked as concealed on the clipboard and are never shown; the paste looks only at the clipboard's change count, never its contents. Without the permission, or when the key events cannot be made, the entry is only copied, and the next history window says so once. The app sandbox stays on and no entitlement is added. The setting is kept in the app's UserDefaults; the permission is kept by macOS, and turning the setting off does not remove it: Settings say so, and you remove it in System Settings → Privacy & Security → Accessibility. macOS shows its alert only the first time the app asks; when the setting is on without the permission, Settings → General offer Open Privacy & Security…, which opens that list (below) and does not ask macOS again. Debug builds only (`#if DEBUG`, for trying paste timing on the Mac): before each paste they read optional keys from the app's own defaults (`debug.paste.settleMs`, `debug.paste.windowWaitMs`, each at most 2 seconds, `debug.paste.commandKey`, `debug.paste.text`, `debug.paste.tap`) that change the waits, whether ⌘ goes down and up around V, whether V carries the text "v", and which event tap is used; they still post only ⌘V, after the same checks. Release builds contain neither the keys nor the code that reads them: `make lint` (`scripts/check_security.py`, `DEBUG_ONLY_STRINGS`) fails if `debug.paste.` appears in the app's sources outside an `#if DEBUG` branch, and `make security` fails if any file of the Release app contains it.
- **Dragging an entry hands it to the app you drop it on.** Dragging a row out of the history window puts that one entry on the macOS drag pasteboard, never on the clipboard, and only because you drag it; the app where you drop it receives it as if you pasted it there. As with the clipboard, macOS lets other apps read the drag pasteboard while the drag lasts. Text and styled text are handed over as they are kept. Copied files are handed over as their file URLs only, never their contents; the app that receives them, such as Finder, opens them with its own rights. An image is a file promise: only when an app accepts the drop does macOS give Show My Copy the place that app chose, and the app then reads the image from its container and writes it there, off the main thread; that copy is the only file the app writes outside its container, and only on your drop. Passwords cannot be dragged: a concealed row starts no drag, and nothing of it reaches the drag pasteboard. The history window accepts no drop of its own rows. Dragging needs no entitlement and uses no `NSWorkspace` or `open…` call (`make lint` checks this as for any file), and it leaves the history and the clipboard as they are.
- **One fixed hand-off: System Settings.** The app never opens links, files or other apps itself (Settings → About shows the address of the source code as text, not as a link), with one exception: the Open Privacy & Security… button asks macOS (`NSWorkspace.open`) to open System Settings at Privacy & Security → Accessibility. It opens one of two fixed `x-apple.systempreferences:` addresses written in the app, `com.apple.settings.PrivacySecurity.extension?Privacy_Accessibility` (tried first on macOS 26 and later) or `com.apple.preference.security?Privacy_Accessibility` (tried first on macOS 15), and the other one only when macOS cannot open the first. It carries no data: nothing you copied or typed, and the code that opens it takes no parameters. Only `ShowMyCopy/Settings/SystemSettingsPane.swift` may do this: SwiftLint's `no_external_handoff` rule excludes only that file, and `make security` fails if that file opens anything but a string literal that starts with `x-apple.systempreferences:`, builds a URL any other way, uses any other way of opening or sharing something, reads the clipboard or takes a parameter. In every other file, app and tests, `make lint` (`scripts/check_security.py`) reads the code with comments and strings removed, so also across line breaks, and fails on any use of `NSWorkspace` other than its read-only `shared.runningApplications`, `shared.frontmostApplication`, `shared.notificationCenter`, `shared.icon` and `shared.urlForApplication` and its notification names, so no file can keep, pass around or create an `NSWorkspace` to open something with; on any member or call whose name begins with the word `open` (`open`, `openURL`, `openApplication`, ...) unless it is one of the app's own names listed in the script, or `SMAppService.openSystemSettingsLoginItems()` (below); on Launch Services, Apple events and the Services menu; on looking up classes, methods or symbols by name (`NSClassFromString`, `Selector("…")`, `dlsym`); and on a file it cannot read. The SwiftLint rule mirrors this in Xcode; the script decides. System Settings is a separate system app: what you do there is up to macOS, and the app only reads the permission again when its Settings come back to the front. (Open Login Items… under Open at login is not this exception: it calls `SMAppService.openSystemSettingsLoginItems()`, where macOS picks the page.)
- **Copies of the app signal each other by name only.** Only one copy of the app runs. A copy that starts while another one runs, such as a build from another folder while the installed app runs, quits before it reads the clipboard or the history, and first posts the distributed notification `com.pandamy619.ShowMyCopy.anotherCopyStarted` with no object and no `userInfo`; the running copy then shows its Settings window. (Opening the same app again from Finder, Spotlight or Launchpad starts no second copy: macOS brings the running one forward, which shows its Settings.) This needs no entitlement: the App Sandbox lets an app post a distributed notification as long as it carries no `userInfo` dictionary (Apple's documentation of `DistributedNotificationCenter.postNotificationName(_:object:userInfo:deliverImmediately:)`), and observing one by its name needs none. Any app or process on the Mac can post this name. The running copy reads nothing from it, neither its object nor its `userInfo`, and does nothing but show its own Settings window, at most once every 3 seconds, so posting it in a loop cannot keep pulling the window forward. A Release build observes no other name, so no other app can make it quit. Debug builds only (`#if DEBUG`, for development): a newer Debug build posts `com.pandamy619.ShowMyCopy.debug.quitForNewerDebugBuild` the same way and a running Debug build quits on it, so any app can quit a Debug build; the newer one waits up to 5 seconds for that, and otherwise quits as above and logs that the other copy can be quit with `pkill -x ShowMyCopy`. The Release build contains neither that name nor the code that posts or observes it: `make lint` (`scripts/check_security.py`, `DEBUG_ONLY_STRINGS`) fails if the name appears in the app's sources outside an `#if DEBUG` branch, and `make security` fails if any file of the Release app contains it. The app does not quit other copies itself: it uses no Apple events and no `NSRunningApplication.terminate()`, which returns false in a sandboxed app.
- **Opens at login only if you turn it on.** The app adds itself to the login items only when you turn on Settings → General → Open at login. It is off by default, and the first launch's Settings only offer it next to the toggle. The app registers itself with `SMAppService.mainApp`: no helper app, no launch agent file of its own and no entitlement, and it runs in its sandbox as when you open it. macOS keeps the login item and lists the app in System Settings → General → Login Items, where you can turn it off; turning the setting off removes it. macOS decides whether it wants your approval there first and may show a notification that a login item was added. The app keeps no copy of the choice: Settings ask macOS each time they open. A change that fails is logged without details.
- **No secrets in logs.** Clipboard contents are never logged.
- **Privacy manifest.** The app carries a privacy manifest (`Contents/Resources/PrivacyInfo.xcprivacy`, from `ShowMyCopy/PrivacyInfo.xcprivacy`): no tracking, no tracking domains and no collected data, since nothing the app reads leaves the Mac. It also gives Apple's reasons for the "required reason" APIs the app uses: UserDefaults for its own settings and the hotkey that KeyboardShortcuts keeps there (`CA92.1`), and file metadata (`C617.1` for the history's own files in the container: their sizes and when a damaged copy was set aside; `3B52.1` for files you copy: their size and whether their data is on this Mac). Apple asks for these reasons on iOS, iPadOS, tvOS, visionOS and watchOS only; the app declares them anyway. It uses no boot time, disk space or active keyboard API on Apple's list. The Control Center extension uses none of these APIs, so it has no manifest. `make lint` (`scripts/check_privacy_manifest.py`) fails when the code of a target starts using a category its manifest does not declare, when a manifest declares one no code uses, says that something is tracked or collected, or holds a key or reason Apple does not list; `make security` checks that the built app carries the manifest unchanged.

### Known limitations

- **Some unmarked passwords are kept.** A password copied without a marker from an app that is not a known password manager — for example from a browser extension or a text file — is kept like any other text, unless a password manager empties the clipboard within 3 minutes. The same rule can remove an ordinary text entry when an app empties the clipboard soon after you copy it and leaves it empty.
- **The first copy after launch, sleep or unlock** has no known source app, so only markers tell whether it is a password, and excluded apps do not apply to it: it is recorded even when an excluded app is in front, since skipping it would lose copies made before launch or on another device meanwhile.
- **Excluded apps are told by the app in front.** The app looks at the clipboard twice a second (less often while macOS lets it nap) and takes a copy for one made in the app that is in front when it notices it, as for password managers. A copy made in an excluded app right before switching to another app can be recorded as that app's, and a copy another app makes in the background while an excluded app is in front is not recorded.
- **Very large copies are read before their size is known.** macOS has no way to tell the size of copied text, styled text or an image before reading it, and the app reads the clipboard on its main thread, since AppKit does not document reading it from another thread as safe. So copying hundreds of megabytes can make the app pause and use that much memory for a moment before it skips the item as too large (text over 1 MB, image data over 20 MB). The app reads as little as it can: one image type, and for styled text the plain text first, skipping the item without reading its larger RTF when the plain text is already too large.
- **Images are decoded in the app's process.** The format allowlist and the pixel limit narrow what reaches ImageIO, but a flaw in one of the allowed decoders (for example WebP) would still run in the process that holds the history.
- **Saved passwords are plain text in memory** while they are kept; the mask only hides them on screen.
- **Expiry waits while the Mac is asleep or locked.** The app does not run while the Mac sleeps and does not look at the clipboard while the screen is locked, so a password whose time is up stays (in memory, and encrypted on disk) until the Mac or its displays wake or the screen is unlocked.
- **Where the encryption key is kept.** The app has no keychain entitlement, so macOS does not let it use the keychain that keeps an item on one Mac only and readable only while the Mac is unlocked. The key is kept in your login keychain instead: Time Machine backs it up, and Migration Assistant can move it to a new Mac together with the history. When the app's code signature changes, for example in a copy you built yourself, macOS asks whether Show My Copy may use the key the next time a password is saved or loaded.
- **Deleted entries may stay on the disk for a while.** The history is an SQLite database. When an entry is deleted (one at a time or by Clear History), expires or is turned into a password, its row is removed and its files are deleted, but SQLite marks the row's old data as free pages without overwriting them, so it can remain in the database file (and for a while in its write-ahead log) and in free disk blocks until it is reused or overwritten. The app does not turn on SQLite's `secure_delete` or incremental vacuum: SwiftData, which the app saves the history with, offers no way to set SQLite options on the connection it opens, `secure_delete` applies only to the connection that sets it, and opening the store with a second connection alongside SwiftData's would risk the store itself. FileVault protects it while the Mac is off or locked. The same goes for the files of deleted images and thumbnails. Passwords are written to disk only encrypted, so this applies to their encrypted form only, unless an entry was saved as normal text before it was recognized as a password.
- **Some details of saved passwords are not encrypted:** when they were copied, from which app, and when they expire.
- **A damaged history file is kept aside for a week.** If the history file cannot be opened, the app tries again and, while the file is a SQLite database (it may belong to another build, or the disk may be full), leaves it in place and keeps the history in memory for that launch. Only when the file is not a database, or it failed to open on 3 launches in a row, is it renamed to `History.store.damaged` (replacing an older one) in the same folder, and a new, empty history starts. The copy holds everything the old history held, out of reach of expiry and the history limits; passwords in it stay encrypted. It counts toward the size on disk in Settings → Storage, which explains it, and it is deleted at the first launch a week after it was set aside, by Clear History, or when Save passwords is turned off. Saved images are kept while it exists.
- **Password manager list.** Some bundle identifiers (Proton Pass, Keeper, LastPass, Enpass, Strongbox Pro) are taken from third-party catalogs and still have to be checked on a Mac; Dashlane and NordPass are not listed yet.
- **A paste lands where the app in front has its focus.** The app checks that the same app is in front before it sends ⌘V, not which window or field inside it has focus: if that app moves its focus in the up to 0.4 seconds after the history window closes, ⌘V goes there. The setting cannot narrow the permission either: macOS lets an app with it post any event, and only the app's code limits it to ⌘V.
- **Screen sharing.** The history window uses the standard macOS opt-out from screen sharing, screenshots and screen recordings. Some newer capture methods (ScreenCaptureKit on recent macOS versions) may still capture it.
